02인증 — JwtAuthenticationFilter

토큰을 읽어 신원을 채우되 차단은 하지 않는 필터. 401 과 403 이 갈리는 지점.

파일: core/security/JwtAuthenticationFilter.java (343줄) 전체 코드베이스에서 가성비가 가장 높은 파일. 모든 요청이 여기를 통과한다. 7월의 102줄에서 343줄로 늘었다. 늘어난 것은 계정 회수(삭제·영구 정지) 판정과 ASYNC 디스패치에서의 SecurityContext 정리(94·119·233줄)다. 핵심 흐름은 그대로다.

401 vs 403 구분

응답의미원인
401 Unauthorized신원 자체가 없음토큰 미첨부 / 만료 / 위조 → SecurityContext 가 비어 있음
403 Forbidden신원은 있으나 권한 부족로그인은 했지만 기능 권한 미달

401이면 토큰 문제, 403이면 권한 문제. 401인데 토큰을 보냈다면 만료됐거나 Bearer 접두사 누락이 대부분이다.

핵심 개념 ① — 순서가 곧 로직 (first match wins)

규칙은 위에서 아래로 검사되고, 처음 매칭된 규칙 하나만 적용된다.

JAVA
.requestMatchers(HttpMethod.POST, "/api/stt/message").permitAll()   // 177줄
.requestMatchers(HttpMethod.POST, "/api/stt/event").permitAll()     // 178줄
.requestMatchers("/api/stt/**").authenticated()                     // 179줄
  • POST /api/stt/message → 177줄에서 걸림 → 인증 불필요
  • GET /api/stt/events → 179줄에서 걸림 → 인증 필요

순서가 반대면 179줄이 전부를 먼저 잡아 177줄은 영원히 도달하지 못한다. → 좁은 규칙(구체적)이 위, 넓은 규칙(/**)이 아래.

같은 패턴 예시 (182·184줄):

JAVA
.requestMatchers("/actuator/health", "/actuator/health/**", "/actuator/info", "/actuator/prometheus").permitAll()  // 좁게 열고
.requestMatchers("/actuator/**").hasRole("ADMIN")                                                                   // 나머지 잠금

핵심 개념 ③ — 기본은 잠금

04로그인 흐름

SecurityConfig 는 토큰을 만들지 않는다. 로그인 요청이 지나가는 길.

SecurityConfig 는 토큰을 만들지 않는다. 두 가지 역할만 한다.

도식
POST /api/auth/login  { username, password }
   │
   ▼
[1] URL 매트릭스 144줄  .requestMatchers("/api/auth/**").permitAll()
        → 통과. 토큰 없어도 안 막음                        ★ 역할 1
   │
   ▼
[2] JwtAuthenticationFilter
        토큰이 없으니 아무것도 안 하고 통과 (발급 전이므로 당연)
   │
   ▼

        ├─ authenticationManager.authenticate(...)   ID/PW 검증
        │     ↑ 이 빈을 SecurityConfig 가 제공         ★ 역할 2

질문답

  • user.handleLoginSuccess(clientIp) (137줄) 가 로그인 실패 카운터를 리셋
  • 계정 잠금 해제(수동): UPDATE users SET loginFailCount=0, accountNonLocked=1 WHERE username='<username>'; (컬럼은 camelCase)

052차 관문 — @PreAuthorize

메서드 단위 인가. 역할 기반과 권한 기반을 언제 고르는가.

403개 파일에서 사용 중. 표현식 빈도 (2026-10-12 실측):

사용 횟수표현식
1,495isAuthenticated()
83hasFeature('도메인:자원:행위')
24hasFeature(...) and hasFeature(...)
20permitAll()
1 · 1hasAnyFeature(...) · hasAllFeatures(...)
1hasMenuPermission('admin')
1hasRole('ADMIN')

7월엔 hasRole('ADMIN') 467건이 1위였고 hasRole('ADMIN') or hasMenuPermission(...) 패턴이 33건 있었다. 전부 이관됐다. 지금의 규칙은 "API 인가는 인증 여부로만, role 하드코딩 금지"(CRITICAL 19)와 "role 판정을 기능 권한으로 옮길 때는 같은 범위 · 관리자 단축 없음 · 호출부 전수"(CRITICAL 27)다.

isAuthenticated() 의 의미

"로그인만 되어 있으면 통과" — 역할도 권한도 보지 않는다. JwtAuthenticationFilter 가 SecurityContext 를 채웠는지만 확인한다.

이것이 기본값인 이유: 누가 무엇을 볼 수 있는지는 메뉴 매트릭스(DB)와 서비스 범위가 정한다. 컨트롤러는 "로그인했나"만 묻는다. 단 permitAll() 은 안 된다 — "본인"을 특정할 수 없기 때문이다.

SELECT DISTINCT m.code, m.name
FROM users u
JOIN user_dynamic_roles ur ON ur.user_id = u.id
JOIN dynamic_roles r       ON r.id = ur.role_id
JOIN role_permissions rp   ON rp.role_id = r.id
JOIN permissions p         ON p.id = rp.permission_id
JOIN menus m               ON m.id = p.menu_id
WHERE u.username = 'admin'
  AND p.permission_type = 'MENU'
  AND p.is_active = 1;

SELECT code, name, permission_type, feature_type FROM permissions

JAVA
// 1. 컨트롤러 — 클래스 레벨은 로그인만
@RestController
@RequestMapping("/api/consultation-history")
@PreAuthorize("isAuthenticated()")
public class ConsultationHistoryController { ... }

// 2. 범위 결정자 — 권한 코드 기반 (배포 없이 조정 가능)
public record AccessScope(boolean viewAll, boolean updateAll, boolean deleteAll, Long userId) {
    public static AccessScope resolve(DynamicPermissionService svc) {
        String username = SecurityUtils.getCurrentUsername();
        Long userId = SecurityUtils.getCurrentUserIdOrThrow();
        return new AccessScope(
            svc.hasPermission(username, "consultation:history:view:all"),
            svc.hasPermission(username, "consultation:history:update:all"),
            svc.hasPermission(username, "consultation:history:delete:all"),
            userId);
    }
}

// 3. 조회 — 범위를 쿼리에 강제 주입 (클라이언트 값 무시)
@GetMapping
public Page<HistoryDTO> list(HistorySearchCriteria criteria, Pageable pageable) {
    AccessScope scope = AccessScope.resolve(permissionService);
    if (!scope.viewAll()) criteria.setOwnerId(scope.userId());   // ★ 덮어쓰기
    return historyService.search(criteria, pageable);
}

// 4. 삭제 — 소유권 + 권한 조합
@DeleteMapping("/{id}")
@PreAuthorize("hasAnyFeature('consultation:history:delete:own','consultation:history:delete:all')")
public void delete(@PathVariable Long id) {
    History target = historyService.findById(id);
    AccessScope scope = AccessScope.resolve(permissionService);
    if (!scope.deleteAll() && !target.getOwnerId().equals(scope.userId())) {
        throw new PermissionDeniedException("삭제 권한이 없습니다");
    }
    historyService.delete(id);
}

권한 코드에 범위를 인코딩하면 ADMIN/SUPERVISOR 같은 역할명이 코드에서 사라진다. → 요구사항 변경 시 DB 만 수정하면 된다. 이것이 CRITICAL 27 의 "같은 범위 · 관리자 단축 없음"이다 — 관리자라고 검사를 건너뛰는 분기를 두지 않는다.

절대 규칙 3가지

  1. 신원은 언제나 토큰에서 — SecurityUtils.getCurrentUserIdOrThrow(). 클라이언트가 보낸 userId 는 관리자 전용 엔드포인트에서만 신뢰한다. > ?userId=123 자체가 나쁜 게 아니다. 일반 사용자도 호출 가능한데 그 값을 믿는 것이 나쁘다.
  1. 범위 필터는 검증이 아니라 덮어쓴다 — criteria.setOwnerId(...). 검증은 빠뜨릴 수 있지만 덮어쓰기는 빠뜨리기 어렵다.
  1. 목록과 단건의 실패 응답이 다르다
    • 목록 → 빈 결과 (Page.empty())
    • 단건 → 404 (403 이 아님) > 403 을 주면 "그 ID 는 존재한다"는 정보가 새어 나가 ID 스캔이 가능해진다. > 실제 코드 주석: "타인 결과 — 존재 여부 노출 방지 (404)"

SSOT 유지

범위 판정 로직은 단일 유틸로 두고 모든 엔드포인트가 그것을 통하게 한다. 엔드포인트마다 따로 판정하면 반드시 어딘가 빠진다.

실제 사례: evaluation/util/MyEvaluationScope.owns(identity, result) — /my 계열이 전부 이것을 쓴다(호출부 4곳).

■기억할 것

  1. 필터는 채우고, 매트릭스가 막는다. 401 이면 토큰 문제, 403 이면 권한 문제.
  2. API 인가는 인증 여부로만. hasRole 은 1건만 남았다. 파괴적 행위는 hasFeature, 범위는 서비스, 메뉴 노출은 매트릭스.
  3. 순서가 곧 로직이다. 좁은 규칙이 위, 넓은 규칙이 아래. 뒤집으면 아래 규칙은 영원히 도달하지 못한다.
  4. @PreAuthorize 는 범위를 표현하지 못한다. '본인 것만'은 서비스 코드에서 신원을 토큰으로부터 뽑아 덮어쓴다.
  5. path 가 BE 메뉴와 FE 레지스트리를 잇는 접착제다. menu-definition.json 과 menu.ts 의 path 가 어긋나면 에러 없이 메뉴가 사라진다.
  6. 단건은 403 이 아니라 404. 존재 여부를 흘리지 않는다.
