stt 모듈 — 모듈 구조 패턴 체득

가장 작은 업무 모듈 하나로 '모듈 읽는 법'을 익힌다. 외부 STT 엔진이 보내는 통화 이벤트와 발화를 받아 저장하고, 실시간으로 뿌리고, 통화가 끝나면 다른 모듈에 알리는 입구 모듈이다. 파일 6개, 메서드 2개만 끝까지 따라가면 나머지 60개 모듈에서 어디를 봐야 할지 알게 된다.

작성 2026-10-12 기준 커밋 f06317ca47 실측 로컬 DB · 통화 107건 · 발화 2,774건

00이 단계의 목표

STT 전문가가 아니라 '모듈 읽는 손'을 만드는 단계. 7월 가이드 이후 바뀐 것부터.

STT 전문가가 되는 게 아니다. 목표는 하나다.

아무 모듈이나 열었을 때 "entity 보고 → DB 보고 → controller 보고 → service 메서드 하나 추적" 이 손에 붙는 것.

stt 는 그 연습용 표본이다. 여기서 익힌 루틴을 2단계 evaluation(275개 파일)에서 그대로 쓴다.

01이 모듈이 하는 일 (한 문장)

입구 모듈이다. 받고, 저장하고, 뿌리고, 끝났다고 알린다.

교환기(교환기 연동 시스템)·AI 소프트폰·배치 수집기가 보내는 통화 시작/종료 이벤트와 발화 문장을 받아, 저장하고, 실시간 화면으로 뿌리고, 통화가 끝나면 "끝났다"고 다른 모듈에 알린다.

도식
 외부 STT 엔진 ──POST /api/stt/event (S/E)──▶ ┐
                                              │  ① 필터 (노이즈·중복 차단)
 외부 STT 엔진 ──POST /api/stt/message ──────▶ ┤  ② DB 저장  stt_events / stt_messages
                                              │  ③ 실시간 전송  WebSocket /topic/stt/...  (또는 Kafka)
                                              └  ④ END 이면 SttCallCompletedEvent 발행
                                                        │
                                                        ▼
                                   assist(상담보조 세션 종료) · orchestration(워크플로우 트리거)
                                   addressbot · simulation  ← 다른 모듈이 구독

stt 모듈은 "입구"다. 분석·평가·요약은 하지 않는다. 그건 sttanalytics(3단계)·evaluation(2단계)·assist 가 이 모듈이 발행한 이벤트를 받아서 한다.

화자 판정 — call_type 이 정답, channel_type 은 함정

실데이터를 보면 왜 헷갈리는지 바로 보인다.

도식
call_type  channel_type  건수
TX         NULL           803   ← 정상 (상담사)
RX         NULL           788   ← 정상 (고객)
IN         MIX            520   ← 화자 미상 (옛 Oracle 동기화: IN=인바운드 방향)
TX         VOICE          171   ← 손으로 만든 JSON 가져오기
TX         TX             161   ← 옛 데이터 (channel_type 에도 화자를 넣던 시절)

channel_type 한 컬럼에 테넌트 ID · 화자 · 매체 세 가지 의미가 섞여 있다(엔티티 주석에 경위가 적혀 있다). 그래서 화자는 반드시 util/SttSpeakerUtils 를 통해서만 판정한다.

  • isAgent(message) → call_type 이 TX 일 때만 true
  • MIX · VOICE · IN · OUT 은 "화자 모름" → 고객으로 떨어진다(기존 호출부 호환)

신규 코드에서 getCallType().equals("TX") 를 직접 쓰지 말 것. 위 유틸이 SSOT 다.

3.3 엔티티 안의 메서드 2개 — "원문은 안 건드린다"

STTMessage 에는 initializeCorrection() · applyCorrection() 이 있다. 규칙은 하나다.

text(원문)는 저장 뒤 절대 수정하지 않는다. 교정은 corrected_text 에 쓰고, 이력은 stt_message_correction_revisions 에 append-only 로 쌓는다.

correction_version 이 1씩 올라가고 revision 행이 하나 추가된다. 로컬 DB 는 revision 0건 — 교정이 돈 적이 없다. (corrected_text 가 2,446건 있는 건 가져오기 때 원문을 복사해 넣은 것이지 교정 결과가 아니다.)

native_ai_softphone같은 DN 에 Bridge 통화 활성 중 들어온 native 발화
native_carryover이미 차단된 native 통화의 나머지 발화·종료
post_call_endEND 이후 들어온 늦은 발화
filler_token요,지,음,어,아,그,네에,음음 1음절 단독 발화
echo_phrase고객(RX) 채널 TTS 에코 — 기본 비활성 (정상 발화 손실 위험)

설정은 application.yml 의 stt.ai-softphone.* · stt.noise-filter.* (206~218줄).

읽으면서 볼 포인트: processEventAndShouldDiscard() 에서 native END 를 차단하면 SttCallCompletedEvent 도 안 나간다 → 요약·워크플로우가 돌지 않는다. "AI 소프트폰 통화인데 요약이 안 떴다"는 문의가 오면 이 메트릭부터 본다.

08이 모듈이 밖으로 내보내는 것 — 다음 단계로 가는 다리

Spring 이벤트 2개가 다음 모듈로 가는 다리다.

stt 는 다른 모듈을 직접 호출하지 않는다(라우팅 서비스 제외). Spring 이벤트 2개로만 말한다.

이벤트발행 시점구독자 (다른 모듈)
SttChunkProcessedEvent발화 저장 직후assist 큐 워커, workspace/proactive (실시간 상담보조)
SttCallCompletedEventEND 저장 직후assist (세션 종료·최종요약), orchestration/trigger (워크플로우), addressbot, simulation

평가(evaluation)는 이 이벤트로 시작하지 않는다.

평가 대상은 EvaluationTargetCollectScheduler 가 10분마다 stt_messages 를 긁어서 모은다. 01 가이드 7절 "스케줄러가 6개다"가 이 얘기다. 2단계에서 확인한다.

구독자 중 조건이 붙은 것이 있다: @EventListener(condition = "!@sttAssistQueueProperties.enabled"). stt.assist-queue.enabled 가 true 면 리스너 대신 영속 대기열이 처리한다(기본 false). 지금은 "두 경로가 있고 설정으로 고른다"만 기억.

AI 호출이 붙으면 모듈이 어떻게 달라지나. 15분.

"AI 호출이 붙으면 모듈이 어떻게 달라지나" 를 보는 2번째 표본. 15분이면 된다.

  • 테이블 counsel_type — 로컬 92행, 트리(parent_id · depth · path = STD-1 …)
  • 일반 CRUD 위에 reclassify(AI 재분류 실행) · merge · similarity-groups(유사 이름 묶기) 가 얹혀 있다
  • 그래서 service/impl/ 에 CounselTypeRaceSafeWriter · StandardCatalogResolver · ReclassificationRunServiceImpl 처럼 실행 이력·동시성 방어가 추가로 생긴다
  • 인가는 클래스 레벨 @PreAuthorize("isAuthenticated()") 하나 — 02 가이드 "role 하드코딩 금지"(CRITICAL 19) 의 모범 사례

stt 와 비교해서 볼 것: "쓰기 한 번"이 아니라 "실행(run) 한 번" 이 단위가 되면 *Run 엔티티와 상태 컬럼이 생긴다. 2단계 evaluation_execution 이 똑같은 모양이다.

■기억할 것

  1. stt 는 입구다. 저장하고 전송할 뿐, 분석·평가·요약은 다른 모듈이 이벤트를 받아서 한다.

  3. 저장 성공 후에만 실시간 전송. 화면엔 보이는데 DB 엔 없는 발화를 만들지 않는다.
  4. 출구는 Spring 이벤트 2개. 평가는 이 이벤트로 시작하지 않고 스케줄러가 긁어간다.
  5. 수신 경로에서 LLM 을 기다리지 않는다. 2026-09-23 에 제거된 동기 교정 호출이 그 사례다.
