Oracle 이관 · 운영 기록

다운타임 30분

1억 2천만 행짜리 컨택센터 운영 DB를 Oracle 12c에서 19c로 옮겼다. 서비스를 내린 시간은 30분, 데이터 손실은 0건. 무거운 작업을 전부 다운타임 밖으로 밀어내고 나면 무엇이 남는지, 그리고 그 과정에서 에러 없이 조용히 틀리는 함정들을 어떻게 시끄럽게 만들었는지에 대한 기록이다.

소스 Oracle 12.2 SE · RAC 2노드 타겟 Oracle 19c SE2 · 단일 인스턴스 규모 테이블 123개 · 1억 2,370만 행 · 21.3GB 결과 다운타임 30분 · 손실 0

01전략 — 왜 무중단 사전 이관인가

이 결정 하나가 다운타임을 3시간에서 30분으로 줄였다.

가장 단순한 이관은 서비스를 내리고, export하고, import하고, 검증하고, 설정을 바꾸고, 다시 올리는 것이다. 문제는 그 전부가 다운타임이라는 점이다. 이 규모에서는 export 11분에 import 24분, 여기에 검증과 통계 수집과 전환 작업을 더하면 서비스 중지가 두 시간 반에서 세 시간 반까지 늘어난다.

핵심 통찰은 이것이다. export와 import는 서비스를 내리지 않아도 된다. FLASHBACK_SCN으로 특정 시점의 일관된 스냅샷을 뜨면 서비스가 돌아가는 중에도 정합성 있는 덤프가 나온다. 그 대신 스냅샷 이후에 들어온 데이터, 즉 델타만 따로 옮기면 된다.

실제 진행 일정
토 21:50  배치 크론 정지
토 22:00  SCN 기록 → export → import → 검증        ← 서비스 가동 중
토 23:00  워터마크 고정 + 델타 1회차 (리허설)       ← 서비스 가동 중
일 07:00  델타 2회차 (중간 점검)                   ← 서비스 가동 중
일 13:45  사각지대 점검                            ← 서비스 가동 중
일 14:00  ★ 서비스 중지
          델타 3회차 (최종) → 시퀀스 보정
          → 설정 교체 → 기동                       ← 다운타임 끝 (30분)

35분짜리 export·import도, 수 분씩 걸리는 통계 수집도 전부 다운타임 밖으로 나갔다. 안에 남은 것은 마지막 몇 시간치 델타와 시퀀스 보정과 설정 교체뿐이고, 전부 초 단위 작업이다.

아무 시스템에나 되는 것은 아니다

이번에 이 전략이 성립한 조건은 네 가지였다.

  1. 델타를 식별할 수단이 있다. 단조 증가하는 시퀀스 발급 PK, 또는 신뢰할 수 있는 수정일시 컬럼.
  2. 변경량이 감당 가능하다. 주말 야간이라 시간당 수백 건 수준이었다.
  3. 삭제가 예측 가능하다. 물리 DELETE는 월 1회 배치뿐이었고, 그 배치를 피해서 작업 창을 잡았다.
  4. 되돌릴 수 있다. 소스를 읽기만 하므로, 실패하면 그냥 넘어가지 않으면 된다.

사전 이관은 실패해도 무료다

토요일 밤 작업은 실패해도 잃는 것이 없다. 이 구조 자체가 최대의 안전장치였다. 되돌리기 어려운 지점은 일요일 14시 단 한 곳이었고, 그 시점에 도달했을 때는 이미 델타를 두 번 리허설한 뒤였다.

이관 날짜 자체가 제약이다

월 1회 삭제 배치가 매월 셋째 토요일에 상담이력과 접촉이력을 대량 DELETE하고, 넷째 토요일에 통계를 지운다. 날짜 조건 델타로는 삭제를 잡을 수 없으므로 무중단 사전 이관은 첫째·둘째 토요일에만 가능했다. 작업일을 고른 것이 아니라 계산해서 나온 것이다.

02Data Pump — 클라이언트는 구경꾼이다

이 구조를 이해하면 당일 사고의 절반이 사라진다.

expdp와 impdp 명령어는 일을 하지 않는다. DB 서버 안의 마스터·워커 프로세스가 일하고, 클라이언트는 진행률을 보여주는 창일 뿐이다. 여기서 실전 지식이 파생된다.

  • SSH가 끊겨도 export는 계속 돈다. 잃는 것은 화면뿐이다.
  • Ctrl+C는 작업을 죽이지 않는다. 대화형 프롬프트로 빠질 뿐이고, CONTINUE_CLIENT로 돌아온다.
  • KILL_JOB만은 금물이다. 작업 취소에 더해 덤프까지 지운다.
  • 끊긴 뒤에는 ATTACH=로 재접속한다. JOB_NAME=을 미리 지정해 두면 편하다.
  • 로그 파일은 서버가 직접 쓰므로 tail -f로 언제든 다시 볼 수 있다.

parfile로 관리한다

명령줄에 파라미터를 늘어놓으면 따옴표 이스케이프 지옥이 된다. 특히 EXCLUDE에 서브쿼리가 들어가면 손쓸 수 없다. parfile은 이스케이프가 필요 없고, 버전 관리가 되고, 당일 오타가 없다.

export.par
DIRECTORY=DUMP_MIG_DIR
DUMPFILE=app_%U.dmp              ← %U : 파일 자동 넘버링
LOGFILE=app_exp.log
SCHEMAS=APP_SCHEMA
PARALLEL=1                       ← SE는 1만 가능
FILESIZE=5G
CLUSTER=NO                       ← RAC에서 단일 노드 실행
FLASHBACK_SCN=__SCN__            ← 자리표시자. 당일 sed 치환
EXCLUDE=TABLE:"IN (SELECT table_name FROM user_tables
                    WHERE table_name LIKE 'TEMP%' OR ...)"

__SCN__ 자리표시자는 의도된 설계다. 치환을 잊으면 숫자가 아니므로 expdp가 즉시 멈춘다. 조용히 잘못 도는 것보다 시끄럽게 멈추는 편이 낫다.

EXCLUDE — 이관은 청소의 기회다

TEMP_*, *BAK*, *BK 패턴 61개(16.6GB)를 제외해 덤프를 21GB로 줄였다. 단, 반드시 사전 검증한다.

bash — 덤프 생성 없이 크기만 계산
expdp ... ESTIMATE_ONLY=YES     # 13초 걸렸다
  • 출력의 테이블 목록에 제외 대상이 안 보이면 패턴이 먹은 것이다.
  • 총량이 예상의 절반으로 나와도 정상이다. BLOCKS 방식은 인덱스를 세지 않는다. 인덱스는 import가 다시 만든다.
  • 이 검증을 건너뛰고 당일 뚜껑을 열면, EXCLUDE 오타를 import가 끝난 뒤에야 알게 된다.

앱이 참조하는 테이블을 빼면 기동이 실패한다

제외 후보 중 한 테이블은 0행인데도 수 GB를 차지하고 있었다. 그런데 JPA @Table 엔티티라서 테이블 자체가 없으면 애플리케이션이 뜨지 않는다. 구조만 가져오도록 QUERY=...:"WHERE 1=0"으로 처리했다. 참고로 그 수 GB는 데이터가 아니라 미회수 세그먼트였고, 이관하면서 자동으로 회수됐다.

Standard Edition의 제약

당일 마주친 에러
ORA-39002: invalid operation
ORA-39094: Parallel execution not supported in this database edition.

SE와 SE2는 Data Pump 병렬을 지원하지 않는다. PARALLEL=2조차 즉시 거부된다. 연쇄적으로 impdp의 병렬 옵션도, DBMS_STATS의 degree도, SQL의 PARALLEL 힌트도 전부 무의미해진다. 에디션은 사전 점검 1순위다. SELECT banner FROM v$version 한 줄이면 되는 것을 안 해서 당일 파라미터를 고쳤다.

무해한 에러와 위험한 에러를 미리 분류한다

import 로그의 “16 error(s)”에 당황하지 않으려면 판정표를 미리 만들어 둔다.

에러판정이유
ORA-39083 + ORA-01917무해타겟에 없는 계정에 GRANT 실패. 데이터와 무관
ORA-39082무해PL/SQL 컴파일 경고. COMPILE_SCHEMA로 해소
ORA-31684중단오브젝트 이미 존재 — 재실행 오염
ORA-01652 / 01653중단공간 부족

grep -oE "ORA-[0-9]+" imp.log | sort | uniq -c로 유형별 개수부터 보면 판단이 빠르다.

NFS uid 불일치

두 서버의 oracle 계정 uid가 달랐다. 공유 NFS에 소스가 만든 덤프는 기본 권한이 640이라 타겟이 읽지 못한다(ORA-39087). export 후 chmod 644가 필수이고, expdp를 재실행하면 권한도 다시 640이 되므로 매번 해야 한다.

03SCN — 한 순간의 사진

서비스를 내리지 않고도 정합성 있는 덤프를 뜨는 원리.

서비스 가동 중에 export하면 테이블 A를 읽는 시각과 테이블 Z를 읽는 시각이 다르다. 그 사이에 트랜잭션이 걸쳐 있으면 테이블 간 정합성이 깨진 덤프가 나온다. A에는 상담이 있는데 Z에는 그 접촉이력이 없는 식이다.

FLASHBACK_SCN=을 주면 Data Pump가 모든 테이블을 그 SCN 시점 그대로 읽는다. UNDO를 이용한 읽기 일관성이고, 결과적으로 덤프 전체가 한 순간의 사진이 된다.

  • UNDO 보존 시간 안에 끝내야 한다. SCN 기록 후 꾸물거리면 ORA-01555가 난다. 그래서 SCN 기록 직후 즉시 expdp를 띄웠고, 오래 걸리는 스냅샷 쿼리는 expdp를 먼저 띄운 뒤 병렬 세션에서 돌렸다.
  • 이 SCN이 모든 후속 작업의 기준선이다. 워터마크 대조도, 델타 경계도, 사각지대 점검도 전부 이 한 점을 기준으로 돌아간다.

3억 9천만을 잃을 뻔한 이야기 — SCN 지수 표기

SELECT current_scn FROM v$database;를 돌렸더니 이렇게 나왔다.

SQL*Plus 출력
CURRENT_SCN
-----------
 1.4560E+13        ← ???

SQL*Plus의 NUMWIDTH 기본값이 10이라 14자리 SCN이 지수 표기로 잘려 보인 것이다.

표시값과 실제값의 차이
표시된 값   1.4560E+13  =  14,560,000,000,000
실제 값                    14,560,394,198,945
차이                          394,198,945  ≈ 약 3시간

이 값을 그대로 parfile에 넣었다면 약 3시간 전 시점으로 export됐을 것이다. 그리고 에러는 나지 않는다. 조용히 틀린 데이터가 만들어질 뿐이다.

해법 — 항상 TO_CHAR로 감싼다
SELECT TO_CHAR(current_scn) AS scn,
       TO_CHAR(SYSTIMESTAMP,'YYYY-MM-DD HH24:MI:SS') AS wall_clock
  FROM v$database;

같은 함정이 치환변수에도 있다. COLUMN x NEW_VALUE var는 “화면에 보이는 값”을 가져가므로 표시 폭이 좁으면 잘린 값이 변수에 들어간다. FORMAT A30을 같이 준다. 또 ACCEPT var NUMBER가 14자리 입력을 거부하는 경우가 있어 CHAR로 받았다. 치환은 어차피 텍스트라 AS OF SCN &var는 그대로 동작한다.

시각으로 거를 때는 항상 앞당긴다

SCN_TO_TIMESTAMP와 TIMESTAMP_TO_SCN은 3초 단위 오차가 있다. 이르게 잡으면 몇 행을 중복 처리할 뿐이고 멱등이면 무해하지만, 늦게 잡으면 놓친다.

04델타 설계 — 이 이관의 심장

처음 설계가 틀렸고, 실측이 그것을 증명했고, 전날 밤에 갈아엎었다.

v1 — NOT EXISTS 방식 (폐기)

처음 설계
INSERT INTO tgt
SELECT * FROM src@LINK s
 WHERE s.PK > (SELECT MAX(PK) - 100000 FROM tgt)
   AND NOT EXISTS (SELECT 1 FROM tgt x WHERE x.PK = s.PK);

중복은 생기지 않는다. 여러 번 돌려도 안전해 보인다. 그런데 치명적 결함이 있다.

실제로 벌어지는 일
토 23:00  델타 1회차 → PK=X 복사됨
일 03:00  소스에서 X가 UPDATE됨 (통화 종료시간 기록 등)
일 07:00  델타 2회차 → X는 이미 있음 → NOT EXISTS가 건너뜀
일 14:00  델타 3회차 → 또 건너뜀
결과      03:00의 수정 내용이 타겟에 영원히 반영 안 됨

NOT EXISTS는 중복은 막지만 갱신은 못 잡는다. 델타를 한 번만 돌린다면 문제가 없지만, 여러 회차로 나누는 순간 앞 회차가 복사한 행이 “이미 있다”는 이유로 갱신에서 배제된다.

이것이 이론이 아니라는 증거 실측 확인

상담이력 테이블은 하루 844 insert에 1,549 update였다. 콜이 인입되면 즉시 INSERT되고, 통화가 끝나거나 상담 내용을 작성할 때 UPDATE되는 생애주기 때문이다. 갱신이 삽입의 두 배다.

v2 — 워터마크 DELETE+INSERT (채택)

최종 설계
-- 워터마크(wm) = import 직후 타겟의 MAX(PK) = export 시점의 MAX(PK)
DELETE FROM tgt WHERE PK > wm;                        -- 델타 영역을 통째로 비우고
INSERT INTO tgt SELECT * FROM src@LINK WHERE PK > wm; -- 소스의 현재 모습으로 다시
COMMIT;

왜 이것이 정답인가.

  1. 갱신이 자동 반영된다. 매 회차 소스의 현재 상태를 통째로 다시 가져오므로 그 사이의 UPDATE가 무엇이었든 상관없다.
  2. 삭제도 자동 반영된다. 소스에서 지워진 행은 다시 들어오지 않는다.
  3. 완전히 멱등하다. 몇 번을 돌려도 결과는 “소스의 현재 모습”으로 수렴한다.
  4. 원본이 안전하다. import된 원본은 전부 PK <= wm이므로 DELETE가 절대 건드리지 않는다. 지워지는 것은 언제나 이전 회차의 델타가 넣은 행뿐이다.
  5. 3회차가 모두 동일하다. 회차마다 동작이 다르면 당일에 헷갈린다. 같은 스크립트를 세 번 돌리는 편이 운영상 압도적으로 안전하다.

비용은 델타 영역을 매번 다시 옮긴다는 것인데, 델타가 수천 건 수준이라 몇 초면 끝난다. 정합성을 사고 성능을 파는 거래인데, 이 규모에서는 거저나 다름없다.

워터마크는 손으로 옮겨 적지 않는다

import 직후 타겟의 MAX(PK)는 export 시점 소스의 MAX(PK)와 같다. 이 등식이 성립하는 순간은 단 한 번, import 완료 직후이자 첫 델타 실행 전이다. 그 순간에 자동으로 붙잡는다.

워터마크 고정
CREATE TABLE MIG_WATERMARK (
  tbl     VARCHAR2(60) PRIMARY KEY,
  max_pk  NUMBER,
  created DATE
);
INSERT INTO MIG_WATERMARK SELECT '테이블명', NVL(MAX(PK),0) FROM 각_테이블;
  • 10자리 숫자 네 개를 종이에 옮겨 적는 일 자체를 없앴다. 하나만 틀려도 경계선이 어긋나고, 그 사실을 한참 뒤에 알게 된다.
  • 델타 스크립트는 이 테이블에서 치환변수로 읽는다. 당일 사람이 입력하는 값은 0개다.
  • CREATE TABLE이라 재실행하면 ORA-00955로 멈춘다. 델타 이후에 실수로 다시 돌려 워터마크가 오염되는 것을 문법 차원에서 차단했다.
  • 검산으로 소스에서 AS OF SCN으로 뽑아둔 값과 대조해 네 개 모두 일치를 확인했다.

사각지대 — 워터마크 아래쪽의 수정

이 방식이 못 잡는 유일한 케이스는 워터마크 이하의 행이 export 이후에 수정되는 것이다. 추측으로 덮지 않고 측정했다.

SQL — 생성 후 얼마 만에 마지막 수정이 일어나는가
SELECT CASE WHEN MOD_DATE - REG_DATE <= 10/1440 THEN '10분 이내'
            WHEN MOD_DATE - REG_DATE <= 60/1440 THEN '10~60분'
            ELSE '1시간 초과' END AS 구간, COUNT(*)
  FROM 상담이력
 WHERE REG_DATE >= TRUNC(SYSDATE)
 GROUP BY ...;

-- 10분 이내 839건 / 10~60분 5건(최대 53.6분) / 1시간 초과 0건

수정 지평선 1시간 실측 확인

상담 레코드는 생성 후 최대 1시간 안에 최종 상태가 되고 다시는 건드려지지 않는다. 따라서 위험 노출은 export 직전 1시간에 생성된 콜뿐인데, 그 시간대 인입이 0건이었다. 사각지대가 실측으로 닫혔다.

그래도 안전망은 남겼다. 전환 직전에, 아직 서비스가 돌고 있는 동안 MOD_DATE >= 기준시각 AND PK <= 워터마크 조건으로 “델타가 못 보는 행”만 정확히 짚어 확인했다. 결과가 없으면 통과이고, 몇 건 나오면 그 PK만 집어서 DELETE+INSERT한다. PK 지정이라 인덱스를 타므로 다운타임 부담이 없다.

델타 대상은 추측이 아니라 측정으로 고른다

“어떤 테이블이 주말에 변하는가”를 코드 리뷰로 다 알아낼 수는 없다. 그런데 Oracle이 이미 세고 있다.

SQL — 부하 0의 변경 통계
EXEC DBMS_STATS.FLUSH_DATABASE_MONITORING_INFO;

SELECT table_name, inserts, updates, deletes, timestamp
  FROM dba_tab_modifications
 WHERE table_owner = 'APP_SCHEMA'
   AND (inserts > 0 OR updates > 0 OR deletes > 0);

이것으로 활동 테이블 55개를 놓고 하나씩 업무 판정을 했다.

테이블판정근거
상담통화이력델타핵심 데이터
통합접촉이력델타물량 최다. 무인 시간에도 외부 인터페이스가 밀어넣는다
콜백이력델타IVR이 외부에서 직접 호출. 상담사가 없어도 쌓인다
고객유형델타막판 추가. 제외했다가 재점검에서 토요일 신규 163건을 발견
로그인이력·메모제외업무 판단. 누락 허용
외부 피드 적재제외파일 기반 배치가 채운다. 크론을 멈추면 파일이 쌓였다가 재개 후 처리된다
사원 마스터제외매일 새벽 MERGE가 전량 덮어쓴다. 자가 치유 구조

여기서 얻은 교훈이 세 가지다.

  • “이 테이블은 안 변해요”를 믿지 말라. dba_tab_modifications로 확인하라. 고객유형이 그렇게 추가됐다.
  • 데이터의 공급 경로를 파악하면 델타가 필요 없는 테이블이 보인다. 파일 큐나 매일 전량 MERGE가 그렇다.
  • 무인 시간에도 쌓이는 테이블이 있다. IVR이나 외부 연동은 사람과 무관하게 돈다. 실제로 일요일 새벽 42건이 외부에서 들어왔다.

05시퀀스 보정 — 타이밍이 전부다

빠뜨리면 기동 직후 첫 저장부터 죽는다.

Data Pump는 시퀀스를 export 시점의 값으로 옮긴다. 그런데 소스는 그 뒤로도 16시간 동안 시퀀스를 계속 소비한다. 보정 없이 기동하면 이렇게 된다.

보정을 빠뜨렸을 때
타겟 시퀀스   535,783,366   (export 시점 값)
타겟 테이블   535,78x,xxx   까지 데이터 존재 (델타로 다 들어옴)

→ 첫 상담 저장: NEXTVAL = 이미 존재하는 PK → ORA-00001

공유 시퀀스는 피해를 곱한다

이번 케이스는 HIBERNATE_SEQUENCE 하나를 네 개의 핵심 테이블이 공유하고 있었다. Hibernate의 공용 시퀀스 전략이다. 보정을 빠뜨리면 상담·접촉·콜백·고객유형이 동시에 죽는다.

SQL — ALTER 문을 사람이 쓰지 않는다
SELECT 'ALTER SEQUENCE '||s.sequence_name
       ||' RESTART START WITH '||(r.last_number + 10000)||';'
  FROM user_sequences s
  JOIN user_sequences@SRC_LEGACY r ON r.sequence_name = s.sequence_name
 WHERE r.last_number > s.last_number;
  • RESTART START WITH는 12.2 이상 문법이다. 구버전은 increment를 크게 잡고 NEXTVAL 한 번 뽑은 뒤 되돌리는 트릭을 쓴다.
  • +10000 여유를 둔다. 번호를 버리는 것은 공짜지만 중복은 장애다.
  • 실행 후 같은 스크립트를 다시 돌려 비교 목록이 비었는지 확인한다. 스크립트가 스스로 검증하게 하는 것이다.

순서가 전부다

델타 최종 → 시퀀스 보정 → 기동. 기동을 먼저 하면 그 사이 들어온 상담이 전부 ORA-00001로 실패한다. 그렇다고 너무 일찍 해도 무의미하다. 중간에 보정하면 소스가 계속 소비해서 격차가 다시 벌어진다. 최종 델타 직후, 기동 직전, 단 한 번이다.

기동 후 첫 검증 항목이 “상담 저장 1건”인 이유도 이것이다. 시퀀스 보정의 성공 여부를 보는 자리다.

06DB Link — 별칭이 착지를 바꾼다

이번 이관에서 가장 미묘하고 교훈이 컸던 발견.

본 시스템의 사원 마스터 테이블은 매일 새벽 Quartz 잡이 DB Link로 형제 스키마 두 곳의 데이터를 MERGE해 온다. 그런데 그 두 스키마는 두 달 전에 이미 19c로 이관된 상태였다. 링크 정의를 열어 보니 이랬다.

user_db_links
BRANCH_LINK → host = 'PRODDB'        ← IP가 아니라 TNS 별칭!

TNS 별칭은 호출하는 서버의 tnsnames.ora가 해석한다. 그러니까 이렇게 갈린다.

같은 별칭, 다른 착지
12c 서버에서 호출 → 12c의 tnsnames → 12c 자신 → 구 스키마 (정지됨)
19c 서버에서 호출 → 19c의 tnsnames → 19c 자신 → 현행 스키마

12c에 있던 새벽 배치는 두 달간 죽은 스키마를 성실하게 동기화하고 있었다. 에러는 한 번도 나지 않았다. 접속도 되고 MERGE도 성공하니까. 데이터만 조용히 낡아갔다.

그리고 반전이 있다. 애플리케이션이 19c로 이관되는 순간 이 문제는 저절로 해소된다. 같은 별칭이 이제 19c를 가리키기 때문이다. 링크도 코드도 고치지 않고 두 달치 드리프트가 끝났다.

SQL — 착지 확정 진단
-- 건수만 봐서는 어느 DB에 착지했는지 모른다. 원격 세션에 직접 물어본다
SELECT SYS_CONTEXT('USERENV','SERVER_HOST'),
       SYS_CONTEXT('USERENV','DB_NAME')
  FROM dual@BRANCH_LINK;

일반화한 교훈

이관할 때는 이 DB를 가리키는 링크와 이 DB가 가진 링크를 모두 전수 조사한다. user_db_links의 host가 IP인지 별칭인지까지 본다. 별칭 링크는 이관 후 착지가 바뀔 수 있다. 이번처럼 좋은 쪽으로든, 나쁜 쪽으로든.

그리고 에러가 없다는 것이 맞게 동작한다는 뜻은 아니다. 죽은 스키마와의 동기화는 완벽하게 성공하면서 완벽하게 무의미했다.

이 성질을 역이용할 수도 있다. 이관용으로 만든 링크는 19c에만 있으므로, “링크가 있는가”로 지금 접속한 서버가 어느 쪽인지 판별했다. 12c에서 워터마크 스크립트를 실수로 돌리는 사고를 스크립트 차원에서 막은 것이다.

07검증 — 어떻게 “맞다”를 증명하나

한 가지 방법에 올인하지 않는다.

오브젝트user_objects 종류별 대조초테이블·인덱스·뷰·시퀀스·함수 누락

Data Pump 로그 diff — 이번 이관 최고의 기법

원래 계획은 123개 테이블을 AS OF SCN으로 전수 COUNT(*)하는 것이었다. 8천만 건 스캔에 운영 부하, 수십 분. 이것을 통째로 버렸다.

export 로그의 rows 값은 FLASHBACK_SCN 시점의 정확한 실측치다. import 로그도 마찬가지다. 그러면 이미 있는 것을 비교하기만 하면 된다.

bash — 비용 0의 전수 검증
grep '^\. \. exported' exp.log | sed -E 's/.*"\."([^"]+)".*[[:space:]]([0-9]+) rows$/\1,\2/' | sort > exp_rows.txt
grep '^\. \. imported' imp.log | sed -E '...' | sort > imp_rows.txt

diff exp_rows.txt imp_rows.txt && echo "✅ 전체 테이블 건수 완전 일치"

검증 수단을 새로 만들기 전에

작업 과정에서 공짜로 생긴 데이터가 없는지 먼저 보라. 비용 0, 부하 0, 즉시, 전수, 그리고 실측이었다. 이미 만들어진 정보를 재활용했을 뿐이다.

num_rows 착시 — 두 번이나 홀렸다

user_tables.num_rows는 실제 건수가 아니라 마지막 통계 수집 때 적어둔 장부값이다. 이관 전후 비교에서 이 착시가 두 번 나왔다.

  • 1차 — 타겟이 34만 건 적어 보였다. Data Pump가 소스의 낡은 통계를 데이터와 함께 실어 왔고, 소스는 export 후 자동 수집으로 장부를 갱신했기 때문이다. 실제 행은 동일했다.
  • 2차 — 이관 후 45개 테이블이 달라 보였다. 전부 dba_tab_modifications의 증감치와 정확히 일치했다. 소스 장부가 낡았던 것이다.

판별법은 last_analyzed를 같이 보는 것이다. 장부가 언제 적힌 것인지 알면 착시가 풀린다. 역이용도 가능하다. 낡은 장부와 새 장부의 차이가 곧 그 기간의 변경량이라, 다른 측정의 교차 검증 수단이 된다. 실제로 타겟 실측에서 소스 장부값을 뺀 값이 토요일 인입량 844와 정확히 맞았다.

리허설 측정 — 미래를 과거로 실험한다

일요일 밤에 일어날 일을 토요일에 알 수는 없다. 하지만 금요일 밤 데이터로 시뮬레이션할 수는 있다. “어제 22시에 이관했다고 치자. 그 이전에 등록된 행 중 그 이후에 수정된 것이 몇 건인가?”

이 리허설로 상담이력은 기존 행 수정이 0건, 고객유형은 126건이라는 테이블별 성격 차이가 드러났고, 그것이 델타 설계를 바꿨다. 금요일이 일요일보다 바쁘므로 이 측정치는 자연스럽게 상한선이 된다.

08애플리케이션·배치 전환

DB만 옮긴다고 끝나지 않는다.

변경을 쪼갠다 — 드라이버와 접속 정보의 분리

배치 서버의 JDBC 드라이버가 ojdbc14(10.2)였다. 19c에는 아예 접속되지 않는다(ORA-28040). 교체가 필수인데, 언제 하느냐가 설계 포인트였다.

ojdbc8은 12c에도 붙는다. 그래서 이렇게 쪼갰다.

두 변수를 겹치지 않게
전날(토)  드라이버만 교체 → 구 DB(12c) 상대로 실제 배치 실행 → 검증
당일(일)  접속 URL만 교체

두 변경을 한 시점에 하면 장애가 났을 때 원인이 드라이버인지 접속 정보인지 가릴 수 없다. 쪼개면 각 단계의 실패 원인이 하나로 좁혀진다.

파일만 바꾸면 클래스패스가 조용히 빈다

기동 스크립트의 CLASSPATH가 jar를 파일명으로 나열하고 있었다. jar 파일만 교체하면 클래스패스에 없는 이름이 남아 조용히 빈다. 스크립트 세 개의 토큰도 함께 고쳐야 했다. 그리고 $JAVA_HOME/jre/lib/ext/ 같은 곳에 구버전이 숨어 있으면 클래스패스보다 우선하므로 find / -name "ojdbc*.jar"로 전수 확인한다.

검증의 결정타 — 실제 로드 경로
java -verbose:class -cp "$CLASSPATH" oracle.jdbc.OracleDriver 2>&1 | grep -i ojdbc
# [Loaded oracle.jdbc.OracleDriver from file:/app/batch/lib/ojdbc8.jar]  ← 이게 증거

설정 파일의 함정 두 개

첫째, 같은 키 중복. java.util.Properties는 키가 두 번 있어도 에러 없이 마지막 값을 쓴다. 주석 처리를 하나 빠뜨리면 조용히 엉뚱한 DB에 붙는다. 교체 후 반드시 확인한다.

bash — 정확히 한 줄이어야 한다
grep '<entry key="db.url"' properties.xml | grep -v '<!--'

둘째, RAC 접속 문자열은 “IP 한 글자 수정”이 아니다. RAC 접속은 (DESCRIPTION=(ADDRESS_LIST=(LOAD_BALANCE=ON)(FAILOVER=ON)...)) 구조라, 단일 인스턴스로 가면 줄 전체가 바뀐다. 당일 손편집은 위험하므로 교체본 파일을 전날 만들어 두고 당일에는 cp 한 번으로 끝냈다. 롤백도 cp 한 번이다.

서버 배포본이 소스 저장소보다 최신일 수 있다

이관 작업에서는 재빌드하지 않는다

배치 소스는 2021년 커밋이 마지막인데 서버 배포본은 2023년이었고, 서버 설정 파일에만 존재하는 키도 있었다. 소스로 재빌드해서 재배포했다면 그 차이가 조용히 사라져 파일 경로가 깨졌을 것이다. 설정 파일과 스크립트만 직접 수정한다. 소스와 배포본의 불일치를 정리하는 것은 별건으로 다룬다.

배치의 세 얼굴 — 정지 전략이 각각 다르다

유형예정지·재개 전략
파일 큐 기반외부 피드 5분 배치그냥 꺼도 된다. 파일이 쌓였다가 재개 시 순차 처리되어 유실이 없다. 실제로 17시간치 480건을 재개 직후 한 번에 소화했다
날짜 기준 재집계통계 배치재실행 시한이 있다. 일요일 안에 수동 실행해야 토요일 통계가 생긴다. 월요일이면 영영 구멍
전량 동기화사원 마스터 MERGE아무것도 안 해도 된다. 다음 실행이 알아서 맞춘다

놓치기 쉬운 것이 두 가지 더 있다. 크론과 앱 내장 스케줄러의 이원화 — 크론을 다 꺼도 앱이 떠 있으면 Quartz 잡은 돈다. 실제로 일요일 새벽 동기화가 그렇게 돌았다. 그리고 failover — standby 서버가 액티브의 생존을 확인하고 배치를 넘겨받는 구조라면, 한 대만 내리면 다른 대가 배치를 시작한다. 반드시 동시에 내린다.

숨은 소비자 — 스키마 계정을 남이 쓰고 있다

전환 후 구 DB 세션을 훑으니 계획에 없던 접속자가 나왔다. 외부 시스템 두 곳이 각각 열 개씩, 그리고 DB Link 두 개. 별도 계정이 아니라 스키마 소유자 계정을 직접 쓰고 있어서 GRANT 조사에 걸리지 않았던 것이다.

SQL — 이관 “전”에 했어야 할 조사
SELECT machine, program, COUNT(*)
  FROM gv$session
 WHERE username = 'APP_SCHEMA' AND type = 'USER'
 GROUP BY machine, program;

외부 소비자는 두 갈래로 찾는다

① dba_tab_privs로 GRANT받은 계정, ② gv$session으로 스키마 계정에 직접 접속하는 머신. 후자는 평상시에 찍어 두어야 보인다. 못 찾은 소비자는 이관 후에도 옛 DB를 보며 조용히 낡은 데이터를 읽는다. 앞서 본 링크 드리프트와 같은 병의 다른 증상이다.

09스크립트 설계 원칙

사람이 실수할 자리를 스크립트가 없앤다. 이것이 전부다.

1. 당일 입력값을 0에 수렴시킨다

손으로 옮겨 적는 값이 많을수록 사고 확률이 곱해진다. 최종 형태에서 당일 사람이 다루는 값은 SCN과 시각 단 두 개였다. 워터마크는 테이블이 기억하고, 시퀀스 보정값은 링크가 읽어 오고, 델타 경계는 치환변수가 나른다.

2. 조용한 실패를 시끄러운 실패로 바꾼다

  • __SCN__ 자리표시자 — 치환을 잊으면 즉시 에러. 조용히 현재 시점으로 도는 것을 막는다.
  • 워터마크 CREATE TABLE — 재실행하면 ORA-00955. 조용한 오염을 막는다.
  • precheck에 WHENEVER SQLERROR EXIT — 전제가 무너지면 그 자리에서 종료한다.

3. 오류 처리 상태를 구간별로 명시한다

WHENEVER SQLERROR는 파일이 아니라 세션 상태다. 한 번 CONTINUE로 두면 그 아래 DML까지 이어진다. 실제로 이 실수가 있었다 — DELETE 성공, INSERT 실패, 그리고 COMMIT. 삭제만 확정되는 구멍이었다.

최종 구조
precheck 구간   EXIT SQL.SQLCODE            (전제 실패 → 즉시 중단)
조회 구간       CONTINUE                    (조회 실패는 치명적이지 않음)
DML 구간        EXIT SQL.SQLCODE ROLLBACK   ★ 어떤 오류든 원상태로
대조 구간       CONTINUE                    (커밋 후이므로)

4. 스크립트가 스스로 검증하게 한다

  • 델타 — 실행 전 건수 표시, 사람 확인(PAUSE), 실행, diff 대조까지 한 파일에서.
  • 시퀀스 보정 — 실행 후 같은 스크립트를 재실행해서 비교 목록이 비면 성공.
  • 워터마크 — 기록 직후 값을 출력해 사전 스냅샷과 눈으로 대조.

5. 멱등으로 만들면 재실행이 복구 전략이 된다

델타가 완전히 멱등하므로 “diff가 0이 아니면 한 번 더 돌린다”가 공식 대응이다. 복잡한 복구 시나리오가 필요 없다. 몇 번을 돌려도 같은 결과라는 성질 하나가 당일의 심리적 부담을 크게 줄인다.

6. 주석에 ‘왜’를 남긴다

이 값이 왜 이 값인지, 왜 그 방식을 버렸는지를 주석에 남겼다. 나중에 누가 “이거 더 올리면 되지 않나?” 하는 것을 막고, 다음 이관에서 판단을 재사용하게 한다.

D-7 ~ D-1 (사전)

  • 에디션 확인(소스·타겟 둘 다). SE면 병렬 전부 1

  • 삭제성 배치 일정 확인 → 이관 가능 날짜 결정
  • 배치 지도 작성 — 크론 + 앱 내장 + failover 구조, 유형 분류
  • JDBC 드라이버 호환성 → 전날 선교체 + 구 DB 상대 검증
  • 설정 파일 — 실제로 읽히는 파일 확정, 교체본 사전 준비, 키 중복 검증

■이번 이관을 관통한 세 문장

  1. 측정이 추측을 이긴다. 델타 대상도, 수정 지평선도, 사각지대도 전부 쿼리 한 줄의 실측이 결정했다. “아마 안 변할 거야”는 한 번도 채택되지 않았다.
  2. 조용한 실패가 시끄러운 실패보다 무섭다. SCN 지수 표기, NOT EXISTS 갱신 누락, 죽은 스키마와의 동기화, 설정 키 중복 — 이번에 만난 굵직한 함정은 전부 에러 없이 틀리는 종류였다. 설계의 절반은 이것들을 에러로 바꾸는 일이었다.
  3. 되돌릴 수 있는 구조가 최고의 안전장치다. 사전 이관은 실패해도 무료였고, 델타는 몇 번을 돌려도 같았고, 전환은 cp 한 번으로 되돌릴 수 있었고, 구 DB는 살아 있었다. 긴장해야 할 순간을 단 하나로 줄인 것, 그것이 이 이관이 30분 만에 끝난 이유다.
