두 개의 OracleDriver

pom.xml 열세 줄이 어떻게 “운영은 되는데 로컬만 죽는” 상황을 만들었는가. 좌표·스코프·전이·중재·클래스로딩이 한 사건 안에서 어떻게 맞물리는지 따라가면, 다섯 개념이 각각의 정의보다 훨씬 오래 기억에 남습니다.

대상 web-app (Spring Boot 1.2.5 / Java 8) 증상 ORA-28040 범인 ojdbc14 10.2.0.4.0

01좌표 — Maven이 “같은 것”을 판단하는 기준

두 드라이버가 공존할 수 있었던 근본 이유는 여기에 있습니다.

Maven은 모든 아티팩트를 좌표(coordinates)로 식별합니다. 전체 형태는 groupId:artifactId:packaging:classifier:version이고, 보통은 앞의 셋만 씁니다.

groupId com.oracle.database.jdbc 배포 주체의 네임스페이스
artifactId ojdbc8 산출물 이름
version 19.21.0.0 버전

파란 두 칸이 동일성 키입니다. 버전은 식별자가 아니라 “골라야 할 값”입니다.

핵심 규칙은 이것입니다. Maven이 “같은 라이브러리”로 보는 단위는 groupId:artifactId(줄여서 GA)이고, version은 그 안에서 하나를 고르는 대상입니다. 그래서 같은 GA가 여러 버전으로 들어오면 Maven이 개입해 하나만 남기지만, GA가 다르면 개입 자체를 하지 않습니다. 서로 아무 관계 없는 별개 라이브러리로 취급하니까요.

groupId도 artifactId도 다릅니다. Maven 입장에서 이 둘은 Jackson과 Gson만큼이나 무관한 라이브러리입니다. 그래서 버전 충돌 해결이 일어나지 않고, 둘 다 클래스패스에 올라갑니다. 여기서 이번 사건의 씨앗이 뿌려집니다.

알아두면 평생 쓰는 상식 — ojdbc 뒤 숫자는 DB 버전이 아니다

ojdbc14는 JDK 1.4용, ojdbc6은 Java 6용, ojdbc8은 Java 8용, ojdbc11은 Java 11용입니다. 지원하는 DB 버전은 version 필드가 말해 줍니다 (19.21.0.0 = 19c 계열 드라이버). “ojdbc14니까 14c겠지”는 흔한 오해이고, 실제로는 존재하지도 않는 버전입니다.

groupId가 com.oracle에서 com.oracle.database.jdbc로 바뀐 것도 역사적 사건입니다. 예전엔 라이선스 때문에 Maven Central 배포가 막혀 사내 저장소에 수동 업로드하던 것을, 2019년부터 오라클이 공식 배포하면서 새 네임스페이스를 썼습니다. 구버전과 신버전의 GA가 다른 이유가 바로 이것이고, 덕분에 둘이 조용히 공존할 수 있게 됐습니다.

02스코프 — 어느 클래스패스에 오를 것인가

의존성을 “쓴다/안 쓴다”가 아니라 “언제 쓴다”로 나누는 장치입니다.

Maven은 클래스패스를 하나로 두지 않습니다. 컴파일할 때, 테스트할 때, 실제로 실행·패키징할 때가 각각 다릅니다. <scope>는 그 의존성이 어느 클래스패스에 참여할지를 정합니다. 여섯 종류가 있습니다.

스코프 컴파일 테스트 런타임·패키징 전이 전형적 용도
compile OOOO 기본값. 명시하지 않으면 전부 이것
provided OOXX servlet-api처럼 컨테이너가 이미 갖고 있는 것
runtime XOOO 코드가 직접 참조하지 않는 구현체 — JDBC 드라이버의 교과서적 정답
test XOXX JUnit, Mockito 등 테스트에서만 쓰는 것
system OOXX 로컬 경로 직접 지정. 사실상 폐기, 쓰지 말 것
import ———— dependencyManagement 전용. BOM 가져오기

파랗게 강조된 행이 이번에 우리가 쓴 스코프입니다.

표에서 test 행을 보세요. 컴파일 클래스패스에도, 런타임·패키징에도 오르지 않습니다. 오직 테스트를 돌릴 때만 존재합니다. 그리고 전이도 되지 않습니다 — 내가 의존하는 라이브러리의 test 의존성은 나에게 따라오지 않습니다. 당연합니다. 남의 테스트 도구가 내 실행 환경에 있을 이유가 없죠.

여기서 자연스러운 질문이 나옵니다. “실행에서 빼려는 거면 provided도 되지 않나?” 일반론으로는 그렇습니다. 하지만 Spring Boot에서는 아닙니다.

왜 provided가 아니라 test인가 실측 확인

Spring Boot의 실행 가능 jar(fat jar)에는 컨테이너가 없습니다. 그래서 Boot는 provided도 jar 안에 넣어 줍니다. spring-boot-maven-plugin 1.2.5의 ArtifactsLibraries 클래스를 직접 열어 보면, jar에 담을 스코프 목록에 정확히 세 개만 등록돼 있습니다.

javap -c ArtifactsLibraries.class — SCOPES 초기화
  9: ldc  #41  // String compile
 21: ldc  #44  // String runtime
 33: ldc  #46  // String provided
 48: putstatic  #10  // Field SCOPES

test는 목록에 없습니다. 즉 provided로 뒀다면 fat jar 안에 그대로 남아 아무것도 해결되지 않았을 것이고, test여야만 실행과 배포 양쪽에서 사라집니다.

03전이 의존성 — 부르지 않은 손님

우리는 ojdbc14를 선언한 적이 없습니다. 그런데 거기 있었습니다.

A가 B를 의존하고 B가 C를 의존하면, A는 C도 함께 받습니다. 이것이 전이 의존성이고, Maven이 Ant보다 편한 가장 큰 이유이자 이런 사고의 가장 큰 원인이기도 합니다. web-app이 ojdbc14를 얻게 된 실제 경로는 이렇습니다.

ojdbc14가 도착하는 경로
web-app
└─ (부모 pom) platform-boot-dependencies
   └─ platform-kernel / framework-boot        scope: compile
      └─ platform-core
         └─ framework-data-jpa
            └─ framework-data
               └─ com.oracle:ojdbc14:10.2.0.4.0  ← 여기

framework-data의 pom이 ojdbc14를 직접 선언하고 있고, 그 위로는 아무도 <exclusion>을 걸지 않았습니다. (부모 pom을 검사한 결과 exclusion 선언은 0건이었습니다.) 더 성가신 건 framework-data-jpa를 참조하는 모듈이 하나가 아니라는 점입니다 — platform-core, framework-file, framework-user, framework-domain, framework-web-endpoint. ojdbc14로 가는 길이 다섯 갈래인 셈입니다. 이 사실은 4절에서 결정적인 의미를 갖습니다.

스코프는 전이되면서 약해진다

전이된 의존성의 스코프는 원래 스코프 그대로가 아니라, 경로상 두 스코프의 조합으로 다시 계산됩니다. 규칙의 요점만 기억하면 됩니다.

  • compile 경로로 온 compile → compile. 이번 케이스가 여기 해당합니다.
  • provided를 거쳐 온 것 → provided (또는 생략).
  • test를 거쳐 온 것 → 아예 생략. 전이되지 않습니다.
  • runtime을 거쳐 온 compile → runtime으로 강등.

경로 전체가 compile이었기 때문에, ojdbc14는 compile 스코프로 우리 프로젝트에 도착했습니다. 컴파일에도, 실행에도, fat jar에도 전부 포함되는 가장 강한 형태로 말입니다.

04중재 — 가장 가까운 선언이 이긴다

Maven이 같은 GA의 후보 여럿 중 하나를 고르는 방법.

같은 GA가 여러 경로로 들어오면 Maven은 중재(mediation)를 수행합니다. 규칙은 단순합니다.

Nearest definition wins — 가장 가까운 선언이 이긴다

루트 프로젝트에서 트리 깊이가 가장 얕은 선언이 채택됩니다. 깊이가 같으면 pom에 먼저 쓰인 것이 이깁니다. 그리고 내 pom에 직접 쓴 선언은 깊이 1이라 언제나 최우선입니다.

중요한 것은 중재가 version만이 아니라 그 선언 전체를 채택한다는 점입니다. 스코프도 함께 따라옵니다. 직접 선언은 전이로 들어온 모든 후보를 무력화하고, 자신의 스코프를 그 GA의 최종 스코프로 확정합니다.

왜 exclusion이 아니라 직접 선언인가

<exclusion>은 특정 경로 하나를 잘라내는 도구입니다. 경로가 다섯 갈래인 이번 상황에서는 다섯 군데에 각각 걸어야 하고, 나중에 여섯 번째 경로가 생기면 조용히 되살아납니다. 반면 직접 선언은 깊이 1이라는 위치의 힘으로 경로 수와 무관하게 한 번에 정리합니다.

<exclusion> 방식

손댈 곳

새 경로
다시 유입됨
가독성

헷갈리기 쉬운 이웃 — dependencyManagement

<dependencyManagement>는 “쓰게 되면 이 버전·스코프로 써라”라는 사전 규격일 뿐, 그 자체로 의존성을 추가하지 않습니다. 반면 <dependencies>에 쓰는 순간 실제로 추가됩니다. 우리가 한 것은 후자입니다. 참고로 dependencyManagement는 중재보다 우선해서 적용되므로, 부모 pom을 고칠 수 있는 상황이라면 거기서 스코프를 지정하는 방법도 있습니다.

05그래서 왜 test가 답인가

여기가 가장 오해하기 쉬운 지점입니다. 천천히 보세요.

1절에서 “GA가 다르면 Maven이 개입하지 않는다”고 했습니다. 그렇다면 이런 의문이 듭니다 — ojdbc8과 ojdbc14는 GA가 다른데, 어떻게 한쪽을 선언해서 다른 쪽을 없앤다는 거지?

답은 둘 사이에 중재가 일어나는 게 아니라는 것입니다. 벌어지는 일은 이렇습니다.

  1. com.oracle:ojdbc14라는 하나의 GA에 대해, 후보가 여섯 개 생깁니다 — 전이 경로 다섯 개(깊이 4~6)와 우리가 직접 쓴 선언 하나(깊이 1).
  2. 같은 GA이므로 중재가 발동하고, 가장 얕은 직접 선언이 이깁니다.
  3. 채택된 선언의 스코프가 test이므로, ojdbc14의 최종 스코프는 test로 확정됩니다.
  4. test는 런타임·패키징 클래스패스에 오르지 않으므로, 실행 시점에 ojdbc14는 존재하지 않습니다.
  5. 그 결과 클래스패스에 남는 Oracle 드라이버는 ojdbc8 하나뿐입니다.

한 줄 요약

ojdbc8이 ojdbc14를 이긴 게 아닙니다. ojdbc14가 자기들끼리 중재된 끝에 test로 확정돼 스스로 무대에서 내려간 것이고, 그래서 ojdbc8만 남은 것입니다.

이 구분이 왜 중요하냐면 — ojdbc8 선언을 추가하는 것만으로는 아무것도 해결되지 않기 때문입니다. 추가는 교체가 아닙니다. 실제로 이 프로젝트는 오래전부터 ojdbc8을 선언하고 있었지만, ojdbc14는 그대로 남아 있었습니다.

06클래스로딩 — 이름이 같으면 벌어지는 일

둘이 공존하면 왜 문제가 되는지, JVM 층위에서.

두 jar가 동시에 있어도, 담긴 클래스 이름이 다르면 아무 일도 없습니다. 문제는 이름이 겹칠 때입니다. 확인해 보면 두 jar 모두 똑같은 두 개의 완전한 클래스 이름(FQCN)을 갖고 있습니다.

unzip -l — 양쪽 jar의 드라이버 클래스
ojdbc14-10.2.0.4.0.jar
  oracle/jdbc/driver/OracleDriver.class   14,943 bytes  (2008)
  oracle/jdbc/OracleDriver.class             489 bytes  (2008)

ojdbc8-19.21.0.0.jar
  oracle/jdbc/driver/OracleDriver.class   21,444 bytes  (2023)
  oracle/jdbc/OracleDriver.class           2,604 bytes  (2023)

JVM의 클래스로더는 클래스패스를 앞에서부터 훑다가 처음 만난 것을 채택하고 즉시 멈춥니다. 버전을 비교하지도, 더 새것을 찾지도 않습니다. 그래서 순서가 전부입니다. 로컬 실행 로그에서 뽑은 실제 순서는 이랬습니다.

80 ojdbc14-10.2.0.4.0.jar 채택됨
84 ojdbc8-19.21.0.0.jar

단 네 칸 차이로 2008년 드라이버가 2023년 드라이버를 가렸습니다.

이 사건의 백미 — ojdbc8이 ojdbc14를 등록해 준다 실측 확인

JDBC 4.0부터 드라이버는 META-INF/services/java.sql.Driver 파일로 자동 등록됩니다. 그런데 확인해 보니 2008년산 ojdbc14에는 이 파일이 아예 없고(JDBC 4.0 이전 산물), ojdbc8에만 있었습니다. 내용은 이렇습니다.

ojdbc8 → META-INF/services/java.sql.Driver
oracle.jdbc.OracleDriver

여기 적힌 건 클래스의 “이름”일 뿐입니다. JVM이 이 이름을 로드하러 가면 클래스패스 순서를 따르고, 앞에 있는 ojdbc14의 클래스를 집어옵니다. 결과적으로 ojdbc8의 등록 파일이 ojdbc14의 드라이버를 등록해 주는 상황이 됩니다. ojdbc14 단독으로는 자동 등록이 안 돼 No suitable driver found가 나는데, ojdbc8을 “고치려고” 추가한 순간 오히려 옛 드라이버가 살아난 셈입니다.

그렇게 살아난 10.2 드라이버는 구형 인증 프로토콜(O3LOGON)을 씁니다. Oracle 19c는 SQLNET.ALLOWED_LOGON_VERSION_SERVER 기본값이 12라 이를 거부하고, ORA-28040: 일치하는 인증 프로토콜 없음을 돌려줍니다. 12c는 받아 주던 것이라 그동안 아무도 몰랐습니다.

스택트레이스 읽는 법

실제 로그에서는 이 한 줄 뒤에 BeanCreationException이 스무 겹 쌓였습니다. 연결이 안 되니 Hibernate가 방언(dialect)을 판정하지 못하고 (Access to DialectResolutionInfo cannot be null), entityManagerFactory가 실패하고, 그것을 주입받는 빈들이 연쇄로 무너진 것입니다. 스무 겹은 전부 2차 피해이고, 원인은 맨 처음 한 줄이었습니다. 긴 스택을 만나면 아래에서 위가 아니라 시간순으로 가장 먼저 찍힌 줄을 찾으세요.

07사건 재구성

같은 pom인데 왜 서버는 살아 있고 로컬만 죽었는가.

클래스패스 순서는 Maven이 의존성을 해석한 순서를 따르는데, 이 순서는 어떤 목표(goal)를 실행하느냐에 따라 달라집니다. spring-boot:run은 test 스코프까지 포함해 해석하고, repackage는 compile·runtime만 해석합니다. 해석 요청이 다르면 결과 집합의 순회 순서도 달라질 수 있습니다.

실행 방식먼저 읽힌 드라이버결과
spring-boot:run (로컬) ojdbc14 ORA-28040 — 기동 실패
fat jar (서버 배포) ojdbc8 정상 — 우연히 살아남음

서버가 ojdbc8을 쓰고 있다는 것은 추측이 아니라 확인된 사실입니다. 개발 19c에 붙어 있는 세션을 조회하니, app-dev-01에서 온 36개 세션이 전부 19.21 드라이버였습니다.

개발 19c — v$session_connect_info
USERNAME     MACHINE   CLIENT_DRIVER              CNT
CENTER_SCHEMA   app-dev-01    jdbcthin : 19.21.0.0.0      9
APP_SCHEMA    app-dev-01    jdbcthin : 19.21.0.0.0     15
BRANCH_SCHEMA   app-dev-01    jdbcthin : 19.21.0.0.0     12

즉 “ojdbc8 선언 덕분에 서버가 돈다”는 말은 결과적으로는 맞지만, 보장된 것은 아니었습니다. ojdbc14가 클래스패스에 남아 있는 한 그것은 순서 운이고, Maven 버전이 바뀌거나 의존성 하나만 추가돼도 서버 쪽에서 순서가 뒤집힐 수 있었습니다. 운영이 무사했던 것은 설계가 아니라 운이었다는 점이 이 사건의 진짜 교훈입니다.

08실무 원칙

같은 사고를 다시 겪지 않기 위한 장치들.

정기 점검 — 무엇이 들어와 있는지 본다

bash
# 특정 아티팩트가 어느 경로로 들어오는지
mvn dependency:tree -Dincludes=com.oracle:ojdbc14

# 실제 런타임 클래스패스에 무엇이 오르는지 (가장 확실)
mvn dependency:build-classpath -Dmdep.outputFile=/dev/stdout -q \
  | tr ':' '\n' | grep -i ojdbc

재유입 차단 — enforcer로 못을 박는다

사람이 기억하는 대신 빌드가 막게 하는 편이 낫습니다. 누군가 나중에 ojdbc14를 다시 끌고 오는 의존성을 추가하면 빌드가 실패합니다.

pom.xml — maven-enforcer-plugin
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-enforcer-plugin</artifactId>
  <executions><execution>
    <id>ban-legacy-jdbc</id>
    <goals><goal>enforce</goal></goals>
    <configuration><rules><bannedDependencies>
      <excludes>
        <exclude>com.oracle:ojdbc14</exclude>
      </excludes>
      <message>ojdbc14는 19c에 접속할 수 없습니다(ORA-28040). ojdbc8을 쓰세요.</message>
    </bannedDependencies></rules></configuration>
  </execution></executions>
</plugin>

배포 산출물 확인 — 실제로 빠졌는지 눈으로 본다

bash
mvn package -DskipTests
unzip -l target/web-app.jar | grep -i ojdbc
# ojdbc8 한 줄만 나오면 정상

운영에서 실제 드라이버 확인

SQL — 지금 붙어 있는 세션이 무슨 드라이버인지
select s.username, s.machine,
       ci.client_driver, ci.client_version, count(*)
  from v$session s
  join v$session_connect_info ci
    on s.sid = ci.sid and s.serial# = ci.serial#
 where s.type = 'USER'
 group by s.username, s.machine, ci.client_driver, ci.client_version;

■기억할 다섯 가지

  1. Maven의 동일성 단위는 groupId:artifactId다. GA가 다르면 같은 기능의 라이브러리라도 충돌 해결 없이 나란히 공존한다.
  2. 추가는 교체가 아니다. 새 드라이버를 선언해도 옛 드라이버는 사라지지 않는다. 교체하려면 옛것을 명시적으로 치워야 한다.
  3. 같은 FQCN이 두 개면 클래스패스 순서가 승자를 정한다. 그 순서는 Maven이 보장해 주지 않으므로, 순서에 기대는 구성은 언젠가 뒤집힌다.
  4. 직접 선언은 깊이 1이라 전이 경로가 몇 갈래든 한 번에 이긴다. 그 선언의 스코프가 곧 그 GA의 최종 스코프가 된다.
  5. 스코프는 “어느 클래스패스에 오를지”를 정한다. Spring Boot fat jar는 provided까지 담으므로, 실행에서 완전히 빼려면 test여야 한다.
